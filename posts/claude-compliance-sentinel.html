How to Stream Claude Compliance Logs into Microsoft Sentinel

Enterprise-only, no built-in Sentinel connector. This post covers the full Logic App pipeline, the permissive schema that keeps it from breaking on spec updates, and five KQL detection queries for roles, API keys, and org settings.

The Compliance API is available to Claude Enterprise plans and is documented at support.claude.com. The full technical spec is a PDF download linked from that article. No Sentinel connector exists. The endpoint is live and the data is useful, but the path from API key to working detection query is entirely on you.

Enterprise plan only. The Compliance API is not available on Pro or Teams. Public Sector organizations are also excluded. If you are not on Enterprise, the API key creation option will not appear in your organization settings.

This is the build I worked through. Every decision, every schema trap, every RBAC elevation you need to plan upfront. It is based on Rev J (API Version 2026-04-20) and covers the Activity Feed endpoint specifically.

What the Activity Feed actually covers

The Activity Feed gives you programmatic access to 260+ activity types across 33 categories: Authentication, Chats, Files, Projects, Customizations (Skills, Commands, Plugins), Integrations, MCP Servers, Organization Settings, Billing, SSO and Directory Sync, SCIM Provisioning, Claude Code, Roles, Groups, GitHub Enterprise, and more. The spec maps 135 of 172 audit log events to compliance activities, with additional types that have no audit log equivalent.

Each activity type carries its own additional_fields shape. The feed is polymorphic. Activities are queryable up to a minute after they occur and retained for six years.

Three things the Activity Feed does not cover are worth calling out explicitly, because none of them are obvious from the spec.

Conversation content. Prompts and model responses do not flow through the Activity Feed. The broader Compliance API does expose content retrieval via separate endpoints (chat messages, file downloads, artifact content, project documents) under the read:compliance_user_data scope. That is a separate build.

Cowork session-level activity. Admin events are logged: org_cowork_enabled, org_cowork_disabled, org_cowork_agent_enabled, org_cowork_agent_disabled. Actions taken inside a Cowork session are not. The spec does not say this. I confirmed it through observed behavior.

Pre-enablement activity. Logging starts the moment the API is enabled. There is no backfill. The spec does not state this either. Same source.

Architecture

Logic App Consumption (Multi-tenant) is the right fit here. One HTTP GET and one Log Analytics POST every 15 minutes. Pay-per-execution pricing, no infrastructure to manage. If you later need complex transformation logic, tighter retry control, or batching, an Azure Function (timer-triggered, C# or Python) is the direct upgrade path with the same pipeline structure.

15-minute polling is a deliberate choice. For environments under a few hundred users, limit=100 per cycle captures everything. For larger deployments, increase the limit (max 5000) or implement cursor-based pagination using after_id. The 1-minute query delay the API enforces is irrelevant at 15-minute intervals.

Custom Log Analytics table is unavoidable. No built-in Sentinel connector for Claude exists. The Data Collector API posts JSON to a _CL table and fields land with type suffixes (_s, _b). The nested data array arrives as data_s, which is a string. All field-level parsing happens downstream in KQL. Microsoft's Logs Ingestion API with a Data Collection Rule is the alternative if you need ingestion-time transformation and schema enforcement, but that adds meaningful setup complexity for a first build.

Step 1: Enable the API and create the key

This happens in claude.ai under Organization settings. Only the Primary Owner can do it.

Navigate to Data and privacy and enable the Compliance API. Then go to Data Management Settings > Compliance access keys, create a key, name it descriptively (e.g., sentinel-activity-feed-readonly), and select scopes.

For a monitoring-only pipeline, select these three scopes:

  • read:compliance_activities
  • read:compliance_org_data
  • read:compliance_user_data

Do not add delete:compliance_user_data. A monitoring pipeline has no business with delete permissions. If your compliance team needs deletion for eDiscovery later, that gets its own key under a separate access control process.

The key is shown exactly once. Copy it and store it in your secrets manager. It will carry the prefix sk-ant-api01-....

Scopes are immutable after assignment. To change scopes, you create a new key and rotate. Keys can be disabled temporarily and re-enabled, or deleted permanently. There is a second key type worth knowing: the Admin Key, created from Claude Console by an org admin. It carries a fixed read:compliance_activities scope and returns 401 on all other Compliance API endpoints. Use it only if your environment is Console/API-only and needs Activity Feed access without chat or file retrieval.

Step 2: Validate the endpoint before touching Azure

Before building anything in the portal, confirm the API responds.

export ANTHROPIC_COMPLIANCE_ACCESS_KEY=sk-ant-api01-your-key-here

curl -H "x-api-key: $ANTHROPIC_COMPLIANCE_ACCESS_KEY" \
  "https://api.anthropic.com/v1/compliance/activities?limit=5"

Two non-obvious things worth calling out here.

macOS only: if you get a 404, the endpoint may not resolve over IPv6. Force IPv4 with curl -4. This does not affect Azure Logic Apps (IPv4 egress by default), but it will silently block local testing until you figure out what is happening.

Header note: the Compliance API requires only x-api-key. Unlike the standard Anthropic Messages API, no anthropic-version header is needed. The spec mentions this but it is easy to miss.

The response envelope is always:

{
  "data": [ ... ],
  "has_more": true,
  "first_id": "activity_abc123",
  "last_id": "activity_xyz789"
}

data contains an array of Activity objects, newest first. has_more indicates whether more results exist. first_id and last_id are pagination cursors. The internal structure of each Activity object varies by type.

Step 3: Create the Logic App

In the Azure portal, create a Consumption (Multi-tenant) Logic App. Standard region and resource group for your security tooling.

Before you start building the workflow, sort out RBAC. If your environment uses PIM, activate before you open the designer. The three permissions you need:

Permission When you need it Contributor covers it?
Microsoft.Logic/workflows/write Creating the Logic App Yes
Microsoft.OperationsManagement/solutions/write First Data Collector connection to workspace Sometimes no
Microsoft.Insights/diagnosticSettings/write Enabling diagnostic settings No

Owner at the subscription level clears all three. Deactivate the elevation once the pipeline is confirmed working. Leaving elevated access open after the build is the kind of thing that surfaces in a least-privilege review three months later.

Step 4: Recurrence trigger

Add a Recurrence trigger. Interval 15, Frequency Minute, Time zone UTC. UTC matters here. Activity Feed timestamps are RFC 3339 / UTC, and daylight saving drift will quietly misalign your TimeGenerated joins if you use a local zone.

Step 5: HTTP action

Add an HTTP action. Method GET, URI https://api.anthropic.com/v1/compliance/activities?limit=100, Header x-api-key set to your Compliance Access Key.

Enable Secure Inputs and Secure Outputs in the action's Settings. This masks the API key and response body in all run history views. Without it, anyone with Logic App run history access can read your key and your org's activity data. Azure will suggest Key Vault as the alternative. For a single-key pipeline with RBAC-controlled Logic App access, Secure Inputs/Outputs is an acceptable control. If your policy requires Key Vault, use Key Vault. The decision should be documented either way.

Step 6: Parse JSON and the schema decision that breaks production runs

Set Content to the Body output from the HTTP action.

The Logic App designer offers "Use sample payload to generate schema." If you paste a curl response, it generates something like this for a claude_chat_created sample:

{
  "type": "object",
  "properties": {
    "data": {
      "type": "array",
      "items": {
        "type": "object",
        "required": [
          "id", "created_at", "organization_id",
          "organization_uuid", "actor", "type"
        ],
        "properties": {
          "id": { "type": "string" },
          "created_at": { "type": "string" },
          "organization_id": { "type": ["string", "null"] },
          "organization_uuid": { "type": ["string", "null"] },
          "actor": {
            "type": "object",
            "properties": {
              "type": { "type": "string" },
              "email_address": { "type": "string" },
              "user_id": { "type": "string" },
              "ip_address": { "type": "string" },
              "user_agent": { "type": "string" }
            },
            "required": ["type", "email_address", "user_id",
                         "ip_address", "user_agent"]
          },
          "type": { "type": "string" },
          "claude_chat_id": { "type": "string" },
          "claude_project_id": { "type": ["string", "null"] }
        }
      }
    },
    "has_more": { "type": "boolean" },
    "first_id": { "type": "string" },
    "last_id": { "type": "string" }
  },
  "required": ["data", "has_more", "first_id", "last_id"]
}

Do not use this schema. It will break.

The required arrays and typed additional_fields are locked to the sample activity type. The next polling cycle will likely return a different activity type. compliance_api_accessed carries request_id, url, request_method, status_code instead of claude_chat_id. Different actor types have different field shapes: unauthenticated_user_actor has unauthenticated_email_address instead of email_address. Schema validation fails and the run stops. You will come back to this an hour later wondering why the pipeline went silent.

The Activity Feed has 260+ activity types and six actor types: user_actor, api_actor, admin_api_key_actor, unauthenticated_user_actor, anthropic_actor, scim_directory_sync_actor. Anthropic adds new types with each spec revision. A strict schema turns every spec update into a pipeline failure. Use this instead:

{
  "type": "object",
  "properties": {
    "data": {
      "type": "array"
    },
    "has_more": {
      "type": "boolean"
    },
    "first_id": {
      "type": ["string", "null"]
    },
    "last_id": {
      "type": ["string", "null"]
    }
  },
  "additionalProperties": true
}

Only the envelope fields are defined. The data array is untyped. first_id and last_id accept null, which the spec defines for empty result sets. No required array. additionalProperties: true. All field-level parsing moves to KQL.

Step 7: Send to Log Analytics

Add a Send Data action (Azure Log Analytics Data Collector connector). Connect to your Sentinel-linked workspace using Workspace ID and Primary Key from Agents management settings. Set the JSON Request body to the Body from the HTTP action (the full response envelope, not the parsed output). Set Custom Log Name to something like ClaudeComplianceLogs (Azure appends _CL).

Sending the full envelope means has_more, first_id, and last_id land in the table alongside data. This is useful. If has_more is ever true in your logs, your polling window missed events and you need to act on it.

Step 8: Failure alerting and diagnostics

The pipeline is silent when it breaks. An HTTP 401 (key revoked or rotated), a schema validation failure, a Log Analytics ingestion issue, or a platform error all look identical from the outside: no new rows in the table. Build the alerting before you trust the pipeline.

In Azure Monitor, create an alert rule scoped to the Logic App. Signal: Runs Failed, Operator: Greater than 0, Evaluation every 15 minutes, Action: email to your security team.

Enable diagnostic settings on the Logic App with WorkflowRuntime logs going to the same Log Analytics workspace. This requires Microsoft.Insights/diagnosticSettings/write, which is the permission from the RBAC table above that Contributor does not cover. If you did not activate that permission before starting, this is when you find out.

Confirming data flow

After the first successful run:

ClaudeComplianceLogs_CL
| take 10

Expected fields: data_s (JSON string of the activities array), has_more_b, first_id_s, last_id_s, TimeGenerated.

To extract individual activities:

ClaudeComplianceLogs_CL
| where TimeGenerated > ago(1h)
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| extend
    activity_id    = tostring(activity.id),
    activity_type  = tostring(activity.type),
    created_at     = todatetime(activity.created_at),
    actor_type     = tostring(activity.actor.type),
    actor_email    = tostring(activity.actor.email_address),
    actor_ip       = tostring(activity.actor.ip_address),
    org_id         = tostring(activity.organization_id)
| project TimeGenerated, created_at, activity_type,
          actor_type, actor_email, actor_ip, org_id, activity_id

Pagination check:

ClaudeComplianceLogs_CL
| where has_more_b == true

This should return no rows. If it returns anything, your polling window is undersized. Increase limit up to 5000 or implement cursor-based pagination before relying on this data for detections.

Detection queries

All queries follow the same structure: parse data_s, mv-expand, filter by activity_type. The pattern is worth internalizing because you will write many variations.

Role changes and privilege escalation

► Show query 
ClaudeComplianceLogs_CL
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| where tostring(activity.type) in (
    "claude_user_role_updated",
    "role_assignment_granted",
    "role_assignment_revoked",
    "rbac_role_assigned",
    "rbac_role_unassigned",
    "primary_owner_transferred"
)
| extend
    actor_email   = tostring(activity.actor.email_address),
    target_user   = coalesce(
        tostring(activity.user_id),
        tostring(activity.target_id),
        tostring(activity.principal_id),
        tostring(activity.new_owner_id)
    ),
    previous_role = tostring(activity.previous_role),
    current_role  = tostring(activity.current_role)
| project TimeGenerated, tostring(activity.type),
          actor_email, target_user, previous_role, current_role

primary_owner_transferred is the one to watch. It is a low-frequency event in any healthy environment. It should never appear unannounced.

API key lifecycle

► Show query 
ClaudeComplianceLogs_CL
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| where tostring(activity.type) in (
    "api_key_created",
    "admin_api_key_created",
    "admin_api_key_deleted",
    "admin_api_key_updated",
    "scoped_api_key_deleted",
    "scoped_api_key_updated",
    "service_key_created",
    "service_key_revoked"
)
| extend
    actor_email = tostring(activity.actor.email_address),
    key_id      = coalesce(
        tostring(activity.api_key_id),
        tostring(activity.admin_api_key_id),
        tostring(activity.service_key_id)
    ),
    scopes      = tostring(activity.scopes)
| project TimeGenerated, tostring(activity.type),
          actor_email, key_id, scopes

Activity volume baseline

Run this first. Before writing detections, you need to understand what normal looks like in your environment. Anomaly-based detection on a feed you have never baselined is noise from day one.

► Show query 
ClaudeComplianceLogs_CL
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| extend activity_type = tostring(activity.type)
| summarize count() by activity_type, bin(TimeGenerated, 1h)
| order by count_ desc

Compliance API self-monitoring

The API logs its own access. compliance_api_accessed records every request against the feed, including the requesting IP and the key used. This is the query that tells you if your key is being used from somewhere it should not be.

► Show query 
ClaudeComplianceLogs_CL
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| where tostring(activity.type) == "compliance_api_accessed"
| extend
    request_ip = tostring(activity.actor.ip_address),
    status_code = toint(activity.status_code),
    api_key_id  = tostring(activity.actor.api_key_id)
| project TimeGenerated, request_ip, status_code, api_key_id

Any IP outside your Logic App's outbound range or your own testing machine is worth investigating before you assume it is noise.

Organization settings changes

► Show query 
ClaudeComplianceLogs_CL
| extend activities = parse_json(data_s)
| mv-expand activity = activities
| where tostring(activity.type) in (
    "claude_organization_settings_updated",
    "org_compliance_api_settings_updated",
    "org_cowork_enabled",
    "org_cowork_disabled",
    "org_sso_toggled",
    "org_sso_connection_activated",
    "org_sso_connection_deactivated",
    "org_ip_restriction_created",
    "org_ip_restriction_updated",
    "org_ip_restriction_deleted"
)
| extend actor_email = tostring(activity.actor.email_address)
| project TimeGenerated, tostring(activity.type), actor_email

The same pattern covers connector and integration changes (mcp_server_created, mcp_server_deleted, integration_user_connected, integration_user_disconnected), skill lifecycle events (claude_skill_created, claude_skill_replaced, claude_skill_deleted, claude_skill_enabled, claude_skill_disabled), and member changes outside business hours (filter org_user_invite_sent and org_user_deleted by datetime_part("hour", created_at)). Swap in the activity type names from the spec. The query structure does not change.

Each of these promotes directly to a Sentinel Scheduled analytic rule with entity mapping (actor_email to Account, actor_ip to IP) and playbook-based response.

Known limitations

No cursor state between runs. Each run fetches the latest 100 activities with no memory of where the previous run ended. If more than 100 events occur in a 15-minute window, older events are silently missed. For most deployments under a few hundred users this is unlikely, but it is not a guarantee. Closing this gap requires persisting last_id in Azure Storage Table and using it as the after_id parameter on the next run.

Cursor direction. One thing the spec buries: after_id and before_id cannot be combined in a single request. To paginate forward through time (toward newer events), use before_id set to the first_id from your previous response. To page backward (toward older events), use after_id set to last_id. Pick a direction and be consistent.

Data Collector flattening. The data array lands as a string (data_s). Column-level indexing, field-level retention policies, and ingestion-time alerting on individual activity fields are not available without a Data Collection Rule and transformation pipeline on top of this setup. For a first build, the KQL overhead is manageable. At scale it becomes a performance consideration.

What is worth building next

Cursor-based pagination is the first real gap. Until it is in place, any detection built on this pipeline has a coverage caveat. The build is not complex: one Azure Storage Table write after each successful run, one read at the start of the next.

The pipeline tells you when skills change, not whether the skill content is acceptable. A governance process for skill review is the complementary control. Activity Feed data surfaces the when and the who. Human review covers the what.

Content-level DLP via the chat message retrieval endpoints under read:compliance_user_data is a separate and more complex build, but the Activity Feed is the right place to start. Know what events are happening before you try to inspect the content behind them.

Closing

The non-obvious parts of this build are the schema decision (strict breaks silently on the next polling cycle), the RBAC elevation for diagnostic settings (Contributor is not enough), and the key management discipline (scopes are immutable, the key is shown once). Everything else follows from the spec if you read it carefully.

What the pipeline gives you is a proper audit surface for Claude Enterprise activity inside Sentinel, queryable with the same KQL you use for everything else. Most teams running Claude Enterprise today have no structured visibility into what is happening at the API and admin layer. This build closes that gap in a few hours.

Build it before users are live, not after you need it.
